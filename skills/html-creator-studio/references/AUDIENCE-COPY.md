# Audience Copy Protocol｜成品文案与用户审核门禁 v1.5

## 一句话原则
**原始附件是内部事实来源，不是观众默认知道的上下文。** 网页文案、演示标题、旁白、字幕、讲解台词应当成为自洽的最终作品；对观众没有意义的“原文说、文章提到、原链接、如上所述、文档第 X 页”等制作过程痕迹，不得进入公开画面或台词。

## 1｜三层文字必须隔离

| 层级 | 允许内容 | 存放位置 | 谁看到 |
|---|---|---|---|
| A 来源事实层 `source` | 原文、页码、URL、引文、核实状态、直接依据 | `source-map.json`，内部材料 | 制作团队 |
| B 制作说明层 `production` | 镜头意图、章节编号、文案修改理由、引用说明、待核实项 | `storyboard.*` 的内部字段、审稿报告 | 用户/Agent |
| C 观众成品层 `audience` | 可直接阅读或听懂的标题、场景过渡、旁白、字幕、行动号召 | `copy-draft.md`、`approved-copy.json`、渲染舞台 | 终端观众 |

观众不一定看到附件，C 层必须**脱离源文件也可理解**。但重要事实、数字、姓名、日期仍须与 A 层一致。不能为去掉“原文说”而去掉必要的可信来源、法律披露或核实提示。涉及需要正式引证时可把引证放在可见脚注、来源页、片尾、片尾字幕，或自然融入口播：例如“国家统计局公布的……”（来源确实可核实）。

## 2｜表达转换规则

禁止的不是词语的字面存在，而是**不必要的制稿元话语**。默认对以下观众稿报警：
- “原文说／原文提到／原文章指出／上面的文字表明／文档中写到／在附件里／根据你给的文档／如前面给出的截图／原链接说／来源链接认为／原表达是……”
- “this document says / the original article states / according to the attached file / as mentioned in the source / the original link says”
- “接下来我们根据这一页PPT/原 PDF 逐段讲解”（除非课程是在**分析这份文档本身**）

**转换示例（只是示意，事实必须查实）：**

| 制作稿（应改） | 成品稿（更适合观众） |
|---|---|
| “原文提到，整个流程分三步。” | “整个流程分为三步：准备、执行和复盘。” |
| “根据这份 PDF 里的数据，增长是 28%。” | “这一阶段的增长率为 28%。”（须保留来源证明在内部映射；若未核实则不能断言） |
| “原链接介绍了新的合成方法。” | “新的合成方法让场景动画可以逐帧控制。” |
| “文档里写的最大优势是风险可控。” | “这套方案的主要优势，是能够更早识别并管理风险。” |
| “原作者说这可能影响公众。” | “这一变化可能影响公众。”（保留观点归属：只有事实支持时这样处理） |

**例外**：文献综述、文章批评、法规逐条解读、对报告/政策文本本身做分析的作品，用户明确要让观众关注来源时，可以说“报告指出”“第 X 条规定”；此时须介绍报告身份、页码或条款，保证观众听得懂，并说明不是不经核实的事实。

## 3｜对不同交付物的写作原则

**HTML 页面**：标题要有明确结论而非“文档内容分析”；按钮必须是真正可执行的动作；图表标签含单位和时间范围；小屏优先可读而非炫技。不要把文档段落原样粘到满屏。

**演讲/口播**：听觉句子自然、简洁，可独立理解；每 1–3 句传达一个明确认知；不要机械说“接下来我们看下一页”；引导语与正文区分；专业术语首次出现时提供必要解释。

**视频字幕**：精炼且与已批准的口播语义同步；除非另获批准，不得由排版 Agent 自行重写已定稿台词；视频上的大字短句允许是旁白的有根据摘要，但关键数字/结论不得偏移。

**解说片头与片尾**：观众在头 3–5 秒知道主题/问题，结尾得到完整结论或合理行动点，而不是“以上是对原文的总结”。

**来源/版权标识**：涉及必须注明的作者、机构、许可或时效的内容，要在成品中以不破坏理解的方式保留。删除制作口吻不等于隐藏事实依据。

## 4｜文案必须先审稿：独立确认关口

在 Web、Video Ready、Dual 的**正式页面内容编排或旁白/字幕动画实施之前**，先输出《观众成品文案审稿包》，至少包含：
1. `copy-draft.md`：网站主标题、章节标题、关键段落、图表标注、CTA；若有视频，逐场旁白、字幕草案、画面短句、预计时长（按语速估算并提示仅供参考）。
2. `copy-source-map.json`：每条关键事实对应来源/核实状态；内部文件，不给普通观众。
3. `copy-review.md`：设计/信息取舍清单，说明哪里压缩了内容、删去什么、要核实什么，标注所有仍需用户决定的说法。
4. 用户明确选择：**批准 / 按意见修改再审 / 仅确认部分段落**。除非有明确的“这些具体文案已审核确认”的历史上下文，不得默认批准；“你决定视觉”不等于“你决定口播和结论”。

**一律先审后做**：用户要求“自由发挥 / 直接做 / 尽快”可减少审美问询，但**不绕过成品文案确认**。用户可以明确申请“先做不含正式文案的视觉技术样片”，允许占位符/已公开的示例，但不得把其当作已批准的正式内容，不能发布。

**修改后作废规则**：用户确认的是某个文案版本 / 文案哈希 / 适用语言 / 场景范围；后续只改变排版、颜色、动画，不影响语义的修订无需重新审核原文案，但改变标题结论、数字、情绪定性、旁白措辞、字幕关键信息等必须重新提交受影响部分。不能将 A 项批准当作 B 项批准。

**状态必须真实**：
- `draft`：AI 起草完成，尚未提交；
- `review_requested`：已发送给用户等待确认；
- `changes_requested`：用户要求修改；
- `approved`：用户明确确认指定版本和范围；
- `partial_approved`：只允许实施所批准范围；
- `prototype_placeholder`：技术样片用，不能冒充正式口播。

## 5｜建议的数据结构

在新项目 `visual-master/approval.json` 中保留原有视觉批准字段，并扩展：

```json
{
  "status": "prototype_unapproved",
  "user_approved_visual_master": false,
  "public_deployment_approved": false,
  "copy_approval": {
    "status": "review_requested",
    "version": "copy-v1",
    "sha256": null,
    "language": "zh-CN",
    "scope": ["web_headline", "web_body", "video_narration", "video_subtitles"],
    "approved_at": null,
    "approved_by": null,
    "evidence_note": "等待用户明确审稿确认，不能标为 approved"
  }
}
```

单独保留 `content/copy-draft.md` 或 `visual-master/copy-draft.md` 和事实来源映射；确认后生成 `approved-copy.json`，记录已确认的完整文本、版本、摘要、批准证据。**不能在没有用户确认时，AI 自行写入 `approved`。** 所有字段仅记录实际事实，不伪造时间、批准者。

仓库内的 `scripts/lint_audience_copy.py` 能查常见元话语与审批状态，生产模式对缺少 `approved` 或哈希不匹配报错；检查命中需由作者审查，机械扫描不保证每句语义自然。脚本还可检查视觉母版的可见文案是否与已确认的版本一致（当 provided `approved-copy.json`）。

## 6｜场景分镜阶段强制产生的内容

每场分别提供：
- `scene_id`：内部场景标识；
- `audience_headline`：观众真正看到的标题；
- `narration`：观众真正听到的台词（如需要）；
- `subtitles`：对应的字幕（如需要）；
- `on_screen_labels`：观众真正看到的标签与数据；
- `source_refs`：**只用于内部验证**的来源项；
- `approval_state`：当前批准状态。

**错误**：把 `source_refs`、内部“第 2 页提到…”自动拼接进 `narration` 或 `on_screen_labels`。同一份数据可以被内部引用，但不能让观众收到生产元话语。

## 7｜提交审稿时的标准措辞

> 我已经把附件内容转化为观众会直接看到和听到的成品文案。下面按场景列出网页标题、关键文案、解说台词（如适用）和预计时长。请确认：① 可以按此版本实施；② 指出需要改的场景或句子；③ 只批准部分场景。**你未确认前，我不会把这版文案作为正式成品写入视频或发布版本。**

注意：文案的事实内容以附件为依据，新增解释/来源必须单独标注；审稿时给用户的是可读的**观众文本**，内部引用与版权信息另页说明，不要把生产注释混入读者正文。
